# Focus Ingestion Engine 产品设计书

> 本文是 FIE 的正式设计基准，整合了设计评审结论（D1–D8，见 `docs/design-review-notes.md`）。
> 实现层遗留问题见 `docs/code-review-notes.md`。约束铁律见 `docs/project-constraints.md`。

## 1. 产品概述

Focus Ingestion Engine（FIE）是一个面向 Agent、AI 编程工具、自动化系统和协作软件的注意力摄取与焦点归因引擎。它通过 hook、webhook、CLI 等入口接收外部事件，判断事件是否代表真实注意力投入，并自动归并到可持续观察的 Focus。

FIE 不是 TODO 工具，也不是聊天归档系统。它的核心价值是把分散在工具、对话、代码修改和自动化运行中的关注信号，转化为可观察、可审计、可同步、且长期收敛的注意力记录。

## 2. 产品目标

验证：hook 驱动的自动摄取比依赖 Agent 主动记录更稳定，且 FIE 能把跨工具事件可靠归因为 Focus check-in，并在长期使用中保持 Focus 数量收敛。

关键目标：

- 降低用户手动维护 Focus 的成本，且**长期不产生需要人工清理的碎片**。
- 让跨工具工作（对话、文件修改、Git、CI）产生统一的注意力轨迹。
- 保留归因理由，避免黑盒式自动记录，并提供纠正闭环。
- 默认保护隐私，支持按来源分级。
- 优先服务本地个人工作流，后续再扩展团队能力。

## 3. 目标用户

- **个人 AI 工具重度用户**：频繁使用 Codex、Cursor、Claude Code、CLI 推进多个项目，需要知道近期真实关注了什么、哪些主题在漂移、哪些阻塞反复出现。
- **Agent 与自动化开发者**：希望工具运行结束后自动留下结构化记录，关注 hook 稳定性、协议开放性和本地可调试性。
- **注意力看板/知识系统用户**：已有看板或知识库，需要 FIE 补齐自动摄取层。

## 4. 核心问题

- 重要注意力信号散落在聊天、终端、Git、PR 和自动化日志中。
- Agent 经常忘记记录 check-in，或粒度不一致。
- 手动整理成本高，长期主题与重复阻塞不可见。
- 直接保存完整对话有隐私风险，也不利于快速观察。
- 不同工具缺少统一的摄取协议与归因规则。
- **自动归因一旦出错，用户无处纠正，系统也无法改进**（本版新增关注）。

## 5. 产品原则

- Hook 优先：尽量从系统事件自动触发。
- 事件优先：接收标准事件，不绑定单一工具。
- 摘要优先：默认保存脱敏摘要，原文可选。
- 幂等优先：重复 hook 或重试不产生重复 check-in。
- 本地优先：MVP 优先本地运行，云同步后置。
- 解释优先：每次匹配、跳过、创建、写入都有理由。
- **收敛优先**：宁可归入已有 Focus 或标低置信待复核，也不轻易新建，防止碎片化。
- **可纠正优先**：任何自动决策都能被用户纠正，纠正数据反哺质量度量。
- 开放协议优先：HTTP、CLI 已支持，MCP、SDK 规划中。

## 6. 核心概念

### 6.1 Attention Event
外部系统传入的原始事件（对话结束、工具调用、文件变更、Git commit、自动化完成、手动标记等）。是待处理信号，不直接等于 check-in。

### 6.2 Focus
系统归纳出的稳定关注对象（项目、问题、风险、方向、调查线索、长期主题）。Focus 不用完成态，而是通过**状态、权重、最近活动、涉及文件、关键词、阻塞和趋势**表达注意力状态。Focus 具有生命周期（见第 8 节）与可选的层级关系（见第 11 节）。

### 6.3 Check-in
一次对 Focus 的关注归因结果，包含发生了什么、是否有阻塞、下一步、涉及文件、置信度，以及来自哪个事件/run。check-in 可被用户纠正（reassign / confirm / drop）。

### 6.4 Ingestion Run
一次摄取处理过程，记录去重、脱敏、提取、匹配、决策、写入、失败与重试。是排查错误与解释自动归因的依据，原始记录不可删除。

## 7. 核心用户旅程

- **7.1 首次配置**：设置端口、数据库、隐私模式、输出路径；通过样例事件看到一次 ingestion run。成功标准：用户能快速启动并验证本地服务可用。
- **7.2 自动摄取**：工具事件经 hook 到达 → 去重、脱敏、判断实质性 → 匹配已有 Focus 或新建 → 写入 check-in。成功标准：无需手动操作即可在下游看到简洁准确的记录。
- **7.3 调试归因**：查看 run 详情，理解命中的关键词、文件、候选 Focus、最终决策与写入目标。成功标准：能判断问题来自输入、提取、匹配还是输出。
- **7.4 纠正归因（本版新增）**：发现归因不准或为低置信记录时，用户可 reassign 到正确 Focus、confirm 确认、drop 误记录、或 merge/archive Focus。成功标准：纠正即时生效、可回溯，并计入修正率指标。
- **7.5 处理隐私敏感工作**：按来源设置隐私模式，高敏来源只上传来源/时间/类型和标签。成功标准：隐私模式改变后保存内容按预期变化，不影响幂等与统计。

## 8. Focus 生命周期（D1）

为防止长期膨胀，Focus 具有明确状态机与收敛机制。

### 8.1 状态

| 状态 | 含义 | 是否参与匹配 |
|---|---|---|
| `active` | 正常关注对象 | 是，含活跃加分 |
| `dormant` | 超过阈值天数（默认 30）无 check-in | 是，但不计活跃加分，默认列表折叠 |
| `archived` | 用户手动归档 | 否，可查询 |
| `merged` | 被合并进 `merged_into` 指向的 Focus | 否，历史 check-in 可回溯至目标 |

### 8.2 创建收敛：双阈值

不再“匹配不足即新建”，改为按最高候选分数分档：

| 最高候选分数 | 决策 | 说明 |
|---|---|---|
| `>= T_match` | `check_in` | 高置信归入已有 Focus |
| `T_create <= 分 < T_match` | `check_in` + `low_confidence` | 归入最高候选但标低置信，进复核队列 |
| `< T_create` | `create_and_check_in` | 确无归属才新建 |

`T_match` / `T_create` 为可配置项，接入文件维度后需重新校准（见第 9、22 节）。

### 8.3 合并与归档
- `merge`：源 Focus 的 check-in 指针改指目标；源置 `merged` 并记 `merged_into`；keywords/paths 并集；活跃时间取较新。软处理、可回溯。
- `archive`：手动归档，退出匹配。
- `sweep`：将超期未活跃的 `active` 置 `dormant`。

### 8.4 活跃度衰减
匹配的“近期活跃”加分按时间分段：≤7 天 +5，≤30 天 +2，>30 天（dormant）0。

## 9. 归因与匹配设计（D2）

### 9.1 提取（Extraction）
规则提取器先判断事件是否值得记录（trivial vs substantive），再提取主题、进展、阻塞、下一步。MVP 用规则与关键词，不把 LLM 作为必需依赖。当来源未提供 `summary` 时，实质性判定退化为类型/文件信号，需谨慎（见第 22 节风险）。

### 9.2 归因信号
兑现“跨工具归因”的关键，是把改同一批文件/同一主题的不同来源事件收敛到同一 Focus。Focus 记忆其涉及过的规范化文件路径（近期若干 check-in 的并集），check-in 亦记录本次涉及路径。

路径在 redaction 之后、matching 之前规范化，保留“完整相对路径 / 目录 / 文件名”三级供分级匹配，规范化不破坏脱敏。

### 9.3 匹配打分

| 维度 | 加分 | 说明 |
|---|---|---|
| 项目名匹配 | +50 | 强信号 |
| 完整相对路径重合 | +25 / 路径（上限 +50） | 最强跨工具信号 |
| Focus 名称命中 | +30（name 长度≥4 且非通用词才计） | 防子串噪音 |
| 同目录重合 | +8 / 目录 | 次强路径信号 |
| 历史 check-in 关键词重合 | +6 / 词（上限 +18） | 主题延续 |
| 事件关键词命中 | +10 / 词 | |
| 同文件名（不同目录） | +4 | 弱信号 |
| 近期活跃 | +5 / +2 / 0（按 8.4 分段） | |

候选按分数降序取前若干，交由决策引擎按第 8.2 节双阈值分档。

## 10. 决策类型（D8）

Decision Engine 输出以下决策，均须持久化 `decision`、`reason`、候选与关键命中依据：

| 决策 | 触发 | 动作 |
|---|---|---|
| `skip` | 事件无实质信号 | 只记录 run |
| `check_in` | 命中已有 Focus（含低置信） | 写入 check-in |
| `create_and_check_in` | 无合适候选 | 新建 Focus 并写入 check-in |
| `update_metadata` | 仅需更新 Focus 名称/标签/描述 | 更新元数据，不新增 check-in |

## 11. Focus 层级与关系（D4）

Focus 支持可选的父子/关联关系，解决“项目级视图 vs 子问题粒度”的两难：

- 一个大项目 Focus 可挂载多个子 Focus（子任务、具体问题）。
- 关系用于视图聚合与匹配传播（子 Focus 命中时可回溯父项目上下文），不改变归因主链路。
- MVP 可先支持“显式关联”（用户/reassign 时建立），自动层级推断后置。

## 12. 反馈与纠正闭环（D3）

自动决策必须可纠正，纠正数据用于度量与迭代。

### 12.1 操作
| 操作 | 作用 |
|---|---|
| `reassign` | 把 check-in 改归正确 Focus，标 `corrected` |
| `confirm` | 确认低置信归因正确，清 `low_confidence` |
| `drop` | 软删误记录（状态字段，不物理删） |
| `merge` / `archive` | Focus 生命周期操作（见第 8 节） |

所有操作写入审计记录（操作者、理由、时间），原始 run/decision 不改动，纠正体现为指针变更 + 审计条目。

### 12.2 度量支撑
- 用户修正率 = 纠正类操作数 / check-in 总数。
- 低置信占比 = 低置信 check-in / 总数。
- 提供统计命令输出上述指标，作为阈值调优反馈。

## 13. 隐私模型（D5）

隐私是核心功能。支持三档模式，并支持**按来源覆盖全局默认**：

| 模式 | 保存内容 |
|---|---|
| `metadata` | 仅来源、时间、类型和白名单标签（最小化） |
| `summary` | 脱敏摘要（默认） |
| `local_raw` | 本地保留脱敏后正文，不上传外部 |

- 全局默认由配置指定；高敏来源（如私人对话）可单独设更严模式，低敏来源（如公开 CI）可放宽，兼顾归因质量与隐私。
- 所有进入提取、匹配、日志、导出、外部同步的内容必须先经统一 redaction 层，禁止任何模块绕过。
- redaction 覆盖 token、密钥、邮箱、Bearer、绝对路径、IP 等，并支持用户自定义关键词。

## 14. 时间与顺序模型（D6）

- 事件携带 `occurredAt`（发生时间，含时区）；归因、活跃度、趋势计算一律基于 `occurredAt`，而非摄取时间。
- 支持乱序、延迟、历史回填事件：批量导入不污染活跃度与趋势。
- 趋势（Focus 状态随时间的变化）基于 `occurredAt` 时间序列聚合。

## 15. 输出与同步模型（D7）

- MVP 输出为 **pull 模式**：通用 JSONL 导出（`fie.checkin.v1`），供任意下游消费，导出不含原始正文。此模式**无“输出失败”场景**。
- 若引入 push 输出（Webhook、MCP、数据库同步），则启用 run 的失败/重试状态机：输出失败不丢 run，记录脱敏错误并允许重试。
- 设计原则：状态机与其对应的输出能力同时存在，避免悬空字段。输出适配器不得重新实现归因决策。

## 16. 接入入口与实现状态（D8）

| 入口 | 状态 |
|---|---|
| HTTP `POST /v1/events/ingest`、`/v1/events/batch` | 已实现 |
| 只读查询 `/v1/runs`、`/v1/runs/:id`、`/v1/focuses` | 已实现 |
| CLI（ingest、runs、focus、export、纠正类命令） | 部分实现，纠正命令为本版新增 |
| JSONL 导出 | 已实现 |
| MCP、SDK | 规划中 |

文档承诺的能力须如实标注状态，避免接入方按文档对接时踩空。

## 17. 信息架构

MVP 以 CLI 与日志为主要观察入口，需保留以下可观察对象：Events、Runs、Focuses（含状态与关系）、Check-ins（含置信度与纠正标记）、Feedback（纠正审计）、Settings（端口、隐私模式与来源覆盖、输出目标、日志路径）。Web UI 后置。

## 18. 非功能要求

- 可靠性：重复事件不重复写入，输出失败可重试（当有 push 输出时）。
- 可解释性：每个自动决策都能追溯规则与候选。
- 可纠正性：归因可被纠正且可回溯。
- 收敛性：长期运行 Focus 数量趋于稳定，不产生大量碎片。
- 隐私：默认不保存完整原文，外部输出必经脱敏，支持按来源分级。
- 性能：单条事件处理秒级完成。
- 可移植性：本地 SQLite 便于备份迁移。
- 可扩展性：新增 Adapter 不改核心决策链路。

## 19. 数据模型概览

核心表：`attention_events`、`ingestion_runs`、`focuses`、`focus_checkins`。事件、run、Focus 与 Check-in 之间的关联由外键维护，不单设关联表。

本版设计新增/变更（DDL 细节见 `docs/design-review-notes.md`）：

- `focuses`：增 `status`、`merged_into`、`last_decayed_at`、`paths_json`。
- `focus_checkins`：增 `paths_json`、`low_confidence`、`corrected`。
- 新增 `focus_events`：纠正与生命周期操作审计（reassign/merge/archive/drop/confirm）。
- Focus 关系：用于层级/关联的表或字段（第 11 节）。

约束：`source + sourceEventId` 唯一；所有变更走幂等迁移通道（不可直接 `ALTER` 于全量 schema 重放）；记录不物理删除，用状态表达。

## 20. 成功指标

- 自动摄取成功率：hook 触发后成功生成 run 的比例。
- 有效归因率：substantive 事件被正确写入或跳过的比例。
- 重复写入率：应接近 0。
- **用户修正率**：由反馈闭环（第 12 节）直接采集，衡量归因质量并驱动阈值调优。
- **Focus 收敛度**：单位时间新建 vs 复用/合并的比例，衡量碎片化程度。
- 隐私违规数：原文/密钥/敏感信息误入输出的次数，应为 0。

## 21. 范围界定

MVP 必做：本地 HTTP 摄取、SQLite 存储、幂等、规则提取、含文件维度的 Focus 匹配、双阈值决策、Focus 状态与手动 merge/archive、纠正类 CLI 与修正率统计、JSONL 导出、JSON Lines 日志、按来源隐私覆盖、基础配置。

暂不做：团队账号与云同步、完整 Web 管理台、多租户权限、向量数据库、自动读取 IDE 私有状态、强依赖 LLM 的归因、自动 Focus 层级推断、push 输出重试队列。

## 22. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 自动归因不准确 | 用户不信任 | 保存决策理由 + run 调试 + 纠正闭环（第 12 节） |
| Focus 碎片化 | 维护成本反升 | 双阈值 + 合并/归档/衰减（第 8 节） |
| 无 summary 时误判实质性 | 噪音 check-in | 文件/类型信号权重可调，低置信标记待复核 |
| 隐私泄露 | 阻碍使用 | 默认摘要 + 统一 redaction + 按来源分级 |
| Hook 来源不稳定 | 事件遗漏 | 支持 CLI、HTTP 多入口，MCP 规划中 |
| 重复事件 | Focus 噪音 | `source + sourceEventId` 唯一约束 |
| 悬空状态机 | 误导排障 | 输出能力与状态机同时引入（第 15 节） |
| 过早依赖 LLM | 成本与不确定性 | MVP 用规则，LLM 作增强 |

## 23. 开放问题

- `T_match` / `T_create` 默认值：接入文件维度后用真实样本校准，写入配置。
- dormant / archive 的天数阈值默认值。
- reassign 是否允许跨 project；merge 是否允许 active 合入 dormant。
- 是否需要为不同来源配置不同隐私模式的 UI/CLI（设计已支持，交互待定）。
- push 输出何时引入，以及重试是队列还是手动 CLI。
- Focus 自动层级推断的时机与算法。
