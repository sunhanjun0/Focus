# Focus Ingestion Engine 产品设计书

## 1. 产品概述

Focus Ingestion Engine，简称 FIE，是一个面向 Agent、AI 编程工具、自动化系统和协作软件的注意力摄取与焦点归因引擎。它通过 hook、webhook、MCP、CLI 和 SDK 接收外部事件，判断这些事件是否代表真实注意力投入，并自动归并到可持续观察的 Focus。

FIE 不是 TODO 工具，也不是聊天记录归档系统。它的核心价值是把分散在工具、对话、代码修改和自动化运行中的关注信号，转化为可观察、可审计、可同步的注意力记录。

## 2. 产品目标

MVP 阶段目标是验证：hook 驱动的自动摄取比依赖 Agent 主动记录更稳定，且 FIE 可以把外部事件可靠归因为 Focus check-in。

关键目标：

- 降低用户手动维护 Focus 的成本。
- 让跨工具工作产生统一的注意力轨迹。
- 保留归因理由，避免黑盒式自动记录。
- 默认保护隐私，只保存必要摘要。
- 优先服务本地个人工作流，后续再扩展团队能力。

## 3. 目标用户

### 3.1 个人 AI 工具重度用户

这类用户频繁使用 Codex、Cursor、Claude Code、CLI 和自动化脚本推进多个项目。他们需要知道近期真实关注了什么、哪些主题正在漂移、哪些阻塞反复出现。

### 3.2 Agent 与自动化系统开发者

这类用户希望工具运行结束后自动留下结构化记录，而不是要求每个 Agent 都手写 check-in。他们关注 hook 稳定性、协议开放性和本地可调试性。

### 3.3 注意力看板与知识系统用户

这类用户已经使用某类看板、知识库、日志系统或个人数据库观察长期工作。FIE 为其补齐自动摄取层，让 Focus 不再只依赖人工或单个 Agent 的自觉记录。

## 4. 核心问题

当前工作流存在以下问题：

- 重要注意力信号散落在聊天、终端、Git、PR 和自动化日志中。
- Agent 经常忘记记录 Focus check-in，或者记录粒度不一致。
- 手动整理成本高，导致长期主题和重复阻塞不可见。
- 直接保存完整对话存在隐私风险，也不利于快速观察。
- 不同工具缺少统一的摄取协议和归因规则。

## 5. 产品原则

- Hook 优先：尽量从系统事件自动触发，不依赖 Agent 主动记忆。
- 事件优先：接收标准事件，而不是绑定某一个聊天工具。
- 摘要优先：默认保存脱敏摘要，原文可选。
- 幂等优先：重复 hook 或重试不能产生重复 check-in。
- 本地优先：MVP 优先本地运行，云同步后置。
- 解释优先：每次匹配、跳过、创建或写入都应有理由。
- 开放协议优先：HTTP、MCP、CLI 和 SDK 都应可接入。

## 6. 核心概念

### 6.1 Attention Event

外部系统传入 FIE 的原始事件，例如对话结束、工具调用、文件变更、Git commit、自动化完成或用户手动标记。Attention Event 是待处理信号，不直接等同于 check-in。

### 6.2 Focus

系统归纳出的稳定关注对象，可以是项目、问题、风险、产品方向、调查线索或长期主题。Focus 不需要完成状态，而是通过权重、健康度、最近活动、阻塞和趋势表达注意力状态。

### 6.3 Check-in

一次对 Focus 的关注归因结果，包含发生了什么、是否有阻塞、下一步是什么，以及该记录来自哪个事件或运行。

### 6.4 Ingestion Run

一次摄取处理过程，用于记录去重、脱敏、提取、匹配、决策、写入、失败和重试信息。它是排查错误和解释自动归因的依据。

## 7. 核心用户旅程

### 7.1 首次配置

用户安装 FIE，设置本地端口、数据库路径、隐私模式和输出路径。系统提供 `.env.example` 和一条测试命令，帮助用户确认本地服务可用。

成功标准：用户能在 5 分钟内启动服务，并通过样例事件看到一次 ingestion run。

### 7.2 自动摄取 Codex 工作

Codex 会话结束后，hook 向 FIE 发送事件。FIE 去重、脱敏、判断是否有实质工作，再匹配已有 Focus 或创建新 Focus，并写入 check-in。

成功标准：用户无需手动操作，即可在下游看板、文件导出或自动化系统中看到简洁、准确的注意力记录。

### 7.3 调试错误归因

当用户发现某条记录归因不准确时，可以查看 run 详情，理解命中的关键词、候选 Focus、最终决策和写入目标。

成功标准：用户能判断问题来自输入事件、提取规则、匹配规则还是输出同步。

### 7.4 处理隐私敏感工作

用户可以将隐私模式切换为 `metadata` 或 `summary`，确保 FIE 不保存完整原文。高敏来源可以只上传来源、时间、类型和摘要标签。

成功标准：隐私模式改变后，新事件按预期减少保存内容，且不会影响幂等和基本统计。

## 8. MVP 功能范围

MVP 必做：

- 本地 HTTP 服务：`POST /v1/events/ingest`。
- SQLite 存储：events、runs、focuses、checkins。
- 幂等机制：基于 `source + sourceEventId` 去重。
- 规则提取器：判断事件是否有实质关注信号。
- 简单 Focus Matcher：基于项目名、文件路径、关键词和最近活跃度。
- Decision Engine：输出 skip、check-in、create+check-in 或 update metadata。
- 通用 JSONL 输出：导出标准 check-in 记录，供下游工具消费。
- CLI：摄取样例、查看 runs、列出 Focus。
- JSON Lines 日志：记录 ingest、decision 和 sync。
- 基础配置：端口、隐私模式、数据库路径、日志路径和输出路径。

MVP 暂不做：

- 团队账号和云同步。
- 完整 Web 管理台。
- 多租户权限系统。
- 复杂向量数据库。
- 自动读取 IDE 私有状态。
- 强依赖 LLM 的归因能力。

## 9. 功能设计

### 9.1 事件摄取

FIE 接收标准 JSON 事件。必填字段包括 `source`、`sourceEventId`、`occurredAt`、`type`。推荐字段包括 `project`、`summary`、`metadata.files`、`metadata.threadId` 和 `metadata.tags`。

### 9.2 脱敏与摘要

所有事件在进入提取和输出前都经过 redaction 层。默认只保存摘要，不保存完整对话。脱敏规则应覆盖 token、邮箱、长文本、绝对路径中的敏感片段和用户配置的关键词。

### 9.3 提取与归因

规则提取器先判断事件是否值得记录，再提取主题、进展、阻塞和下一步。MVP 使用规则和关键词，不把 LLM 作为必需依赖。

### 9.4 Focus 匹配

Matcher 根据项目名、文件路径、关键词、最近活跃时间和历史 check-in 计算候选 Focus。若分数超过阈值，写入已有 Focus；否则建议创建新 Focus。

### 9.5 输出同步

MVP 优先提供通用 JSONL export 能力，后续可扩展到 Webhook、MCP、数据库同步或第三方工具。输出失败不能丢失 ingestion run，系统应记录失败原因并允许重试。

## 10. 信息架构

MVP 可以先不做完整 Web UI，但需要保留以下可观察对象：

- Events：外部输入事件列表。
- Runs：每次处理过程和最终决策。
- Focuses：系统识别出的关注对象。
- Check-ins：写入 Focus 的归因记录。
- Settings：端口、隐私模式、输出目标和日志路径。

CLI 和日志是 MVP 的主要观察入口。Web UI 可在后续版本中补充。

## 11. 非功能要求

- 可靠性：重复事件不重复写入，失败可重试。
- 可解释性：每个自动决策都能追溯规则和候选结果。
- 隐私：默认不保存完整原文，外部输出必须经过脱敏。
- 性能：单条事件处理应保持秒级完成。
- 可移植性：本地 SQLite 数据库应便于备份和迁移。
- 可扩展性：新增 Adapter 不应修改核心决策链路。

## 12. 成功指标

MVP 验证阶段关注以下指标：

- 自动摄取成功率：hook 触发后成功生成 run 的比例。
- 有效归因率：substantive 事件被正确写入或跳过的比例。
- 重复写入率：重复 hook 造成重复 check-in 的比例，应接近 0。
- 用户修正率：用户需要手动纠正 Focus 归因的比例。
- 隐私违规数：原文、密钥或敏感信息误入输出的次数，应为 0。

## 13. 里程碑

| 阶段 | 时间 | 目标 | 产出 |
|---|---:|---|---|
| M0 | 0.5 天 | 初始化项目 | TypeScript、SQLite、配置、日志 |
| M1 | 1 天 | 完成 Ingest API | HTTP endpoint、事件表、幂等 |
| M2 | 1 天 | 完成规则归因 | Extractor、Matcher、Decision Engine |
| M3 | 0.5 天 | 完成通用输出 | JSONL export 与失败记录 |
| M4 | 0.5 天 | 完成 CLI 调试工具 | ingest、runs tail、focus list |
| M5 | 1 天 | 完成真实 hook 验证 | Codex 或通用 webhook 跑通 |

建议第一版控制在 4-5 天内完成，避免过早扩展 UI、云同步和团队权限。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 自动归因不准确 | 用户不信任记录 | 保存决策理由，提供 run 调试入口 |
| 隐私泄露 | 阻碍使用 | 默认摘要模式，统一 redaction 层 |
| Hook 来源不稳定 | 事件遗漏 | 支持 CLI、HTTP、MCP 多入口 |
| 重复事件过多 | Focus 噪音增加 | 强制 `source + sourceEventId` 唯一约束 |
| 过早依赖 LLM | 成本和不确定性上升 | MVP 先用规则，LLM 作为增强能力 |

## 15. 开放问题

- 第一版是否只支持 Codex hook，还是同时支持通用 webhook 示例？
- 输出适配器写入失败时，是否需要自动重试队列，还是先提供手动重试 CLI？
- Focus 创建阈值应默认保守还是积极？
- 是否需要为不同来源配置不同隐私模式？
- Web UI 是否在 MVP 后立即进入，还是先扩展更多 Adapter？
